## Phase Boundary

<decisions>
## Implementation Decisions

### Setup Experience — env.sh Script

- **`.env`** is hand-maintained, always present — NOT generated from a template
- **`.env.example`** documents all necessary variables with warning comments for any that are missing from `.env` but required
- If `.env` already exists during setup: **skip and notify** — do not overwrite
- **`./bin/env.sh`** is a standalone executable with subcommands: `load`, `show`, `substitute-all`, `check`, `clean`, `help`
  - `load` — sources `.env` and exports as shell environment variables; validates all required variables from `.env.example` exist (in `.env` or environment); warns about missing ones
  - `show` — displays all variables in **plaintext** (no masking, developer tool)
  - `substitute-all` — processes `.template` files into config files using `@VARIABLE_NAME@` placeholder syntax (Maven-style delimiters); prints each file as it generates (`pom.xml.template → pom.xml`); **warns and stops** if any referenced variable is not found in environment
  - `check` — compares timestamps of templates vs generated files; warns if template is newer (meaning `substitute-all` should be re-run)
  - `clean` — removes all generated config files, reverting to template-only state
  - `help` — lists all subcommands with one-line usage examples
- Variables can come from **`.env` OR already-exported environment variables** (e.g., sensitive values like user/password set externally for privacy)
- **Template file list** maintained in `bin/env-templates.list` — plain text, one template path per line, `#` for comments. Upgradeable without editing env.sh
- **Colored output**: green for success, red for errors, yellow for warnings
- Must run from **project root** — error if not in correct directory
- Exception: `source ./bin/env.sh load` must be sourced (inherent to shell export behavior)

### Setup Experience — Template System

- Config files generated from `<filename>.<ext>.template` files using `@VARIABLE_NAME@` placeholder syntax
- Generated files live in **same directory as template**, dropping `.template` extension (e.g., `pom.xml.template → pom.xml`)
- Generated config files are **gitignored**; template files are committed
- **All these files have .template versions**: `pom.xml`, `compose.yaml`, `application-dev.yml`, `application-prod.yml`, `Dockerfile`, `servers.json` (PgAdmin)
- **`application.yml`** (base config) is committed as-is — NOT templated. Only profile-specific YAML files are templated
- Which files to process is defined in **`bin/env-templates.list`** — not hardcoded in script

### Setup Experience — Documentation

- **README**: both a 5-line quick-start sequence (clone → edit .env → source env.sh load → env.sh substitute-all → run) AND a link to detailed `doc/` guide

### Dev/Prod Parity — Flyway Migrations

- **Separate migration directories per profile**: `db/migration/dev/` (H2) and `db/migration/prod/` (PostgreSQL) — fully independent, no shared directory
- **Same version numbers and names** across dev and prod (e.g., `V1__create_users.sql` in both) — different SQL syntax allowed, structure must match
- Flyway auto-detects migration location based on active profile using **Spring's vendor-specific migration support** (convention-based, not configured in YAML)
- **Schema comparison test** runs as part of the regular test suite (`mvn test`) — verifies dev and prod migrations produce the same table structures

### Dev/Prod Parity — Startup Banner

- **Both profiles** show a startup banner: `[DEV MODE] Using H2 in-memory database` / `[PROD MODE] Using PostgreSQL`
- Dev banner **includes config info**: active profile, .env location, number of generated config files present
- H2 console **enabled in dev** mode for database debugging

### Dev/Prod Parity — Seed Data

- Dev profile **auto-seeds** test data on startup: user `tiziano` / `tizianobellin@yahoo.com` with ADMIN role
- No other test users needed — just the project test user from PROJECT.md

### Docker Workflow — Compose Configuration

- `compose.yaml` is a **template** (`compose.yaml.template`) — generated by `env.sh substitute-all`, consistent with template system
- Container names use a **project-specific prefix** (e.g., `usermgmt-app`, `usermgmt-db`, `usermgmt-pgadmin`)
- **All ports configurable via `.env`**: `APP_PORT`, `DB_PORT`, `PGADMIN_PORT`
- **Named volume** for PostgreSQL data persistence (survives `docker compose down`; `docker compose down -v` to reset)
- **Health checks**: PostgreSQL container uses `pg_isready`; app container uses `depends_on` with `condition: service_healthy`
- **db-only profile**: `docker compose --profile db-only up` runs PostgreSQL + PgAdmin without the app (for local dev against real PostgreSQL)
- No Docker convenience wrapper scripts — **document docker compose commands** in docs instead
- Standard Docker logging — `docker compose logs -f app` is sufficient

### Docker Workflow — Build

- **Multi-stage Dockerfile** (already decided in 01-07): Maven build inside container, copy JAR to runtime image
- **Dockerfile is a template** (`Dockerfile.template`) — generated by `env.sh substitute-all`
- Developer **runs `env.sh substitute-all` before** `docker compose build` — build uses pre-generated files from the build context

### Docker Workflow — PgAdmin

- PgAdmin **pre-configured** to connect to PostgreSQL via `servers.json` mounted into the container
- `servers.json` is a **template** (`servers.json.template`) with DB credentials from `.env`

- Exact env.sh shell implementation details (error codes, argument parsing)
- Schema comparison test implementation approach
- Banner formatting and positioning in startup sequence

<specifics>
## Specific Ideas

- env.sh should feel like a proper CLI tool: colored output, help command with examples, clear error messages
- Template system should be fully declarative: add a line to `bin/env-templates.list` to include a new template — no script changes needed
- "I want it like pg_dump" philosophy for env.sh — familiar to developers, works in CI, no interactive prompts
- The developer runs `env.sh substitute-all` before Docker build — the Docker build context expects pre-generated files
