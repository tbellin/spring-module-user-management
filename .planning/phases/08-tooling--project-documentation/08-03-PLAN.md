**doc/02-architecture.md — Architecture Guide**

Write an architecture overview covering:

1. **Tech Stack**: Spring Boot 4.0.1, Spring Framework 7, Java 21, Maven, Spring Modulith 2.0.1, Spring Security (dual filter chain), JJWT, Thymeleaf + Bootstrap 5, Flyway, H2 (dev) / PostgreSQL (prod), SpringDoc OpenAPI 3.0.1.

2. **Module Structure**: Three Spring Modulith modules:
   - `shared` — Cross-cutting: DTOs (UserDto), exceptions, configuration (AppProperties, PasswordConfig, OpenApiConfig), base entities, home controller, global exception handler
   - `user` — User management: JPA entities (AppUser, AppRole) in user.internal, repositories in user.internal, UserService as public API, admin DTOs
   - `auth` — Authentication: JWT (JwtService), login/register (AuthService, AuthController), email verification (VerificationService), password management (PasswordService), admin operations (AdminController, AdminInviteService), security config (SecurityConfig, JwtAuthenticationFilter) — all in auth.internal except JwtService

3. **Security Architecture**: Dual SecurityFilterChain — API chain (@Order 1, /api/**, stateless, JWT Bearer) and Web chain (@Order 2, /**, session-based, form login, CSRF). JwtAuthenticationFilter validates tokens on API requests. BCrypt password hashing. SEC-01 compliance (no user enumeration).

4. **Database Strategy**: H2 with PostgreSQL compatibility mode for dev (zero setup), PostgreSQL for prod (Docker). Flyway manages all schema. Vendor-specific migration directories (h2/, postgresql/). Seed data only in h2/.

5. **Configuration System**: .env.template -> bin/setup.sh generates .env -> bin/env.sh loads vars -> bin/env.sh substitute-all replaces @VARIABLE@ in .template files to produce config files.

6. **Key Design Decisions**: Brief table referencing PROJECT.md decisions — why email as username, why jjwt-gson, why sealed results for verification/password-reset, why modulith over microservices.

**doc/03-api-reference.md — API Reference**

Write an API reference covering:

1. **Overview**: All endpoints under /api/v1/. Authentication via Bearer JWT token. Swagger UI available at /swagger-ui.html for interactive testing. OpenAPI spec at /v3/api-docs.

2. **Authentication**: How to obtain a JWT — POST /api/v1/auth/login, include token as `Authorization: Bearer <token>` header. Remember-me option for 7-day tokens.

3. **Endpoint Catalog** — organized by section, each with:
   - Method, path, auth requirement
   - Request body (JSON example)
   - Response (status code, body example)
   - cURL example

   **Public Endpoints:**
   - POST /api/v1/auth/register — body: `{email, password, firstName, lastName}` — 201
   - POST /api/v1/auth/login — body: `{email, password, rememberMe}` — 200 with `{token, email, displayName, roles}`
   - POST /api/v1/auth/resend-verification — body: `{email}` — 200
   - POST /api/v1/auth/forgot-password — body: `{email}` — 200
   - POST /api/v1/auth/reset-password — body: `{token, newPassword, confirmPassword}` — 200
   - GET /actuator/health — 200

   **Authenticated Endpoints (Bearer token required):**
   - GET /api/v1/users/me — 200 with user profile
   - PUT /api/v1/users/me — body: `{displayName, firstName, lastName}` — 200
   - POST /api/v1/auth/change-password — body: `{currentPassword, newPassword, confirmPassword}` — 200

   **Admin Endpoints (ROLE_ADMIN required):**
   - GET /api/v1/admin/users — query params: search, role, status, page, size, sort — 200 with paginated list
   - POST /api/v1/admin/users — body: `{email, username, firstName, lastName, enabled, roles}` — 201
   - PUT /api/v1/admin/users/{id} — body: `{firstName, lastName, roles}` — 200
   - PATCH /api/v1/admin/users/{id}/status — body: `{enabled}` — 200

4. **Error Responses**: Standard ProblemDetail format (RFC 9457). Common status codes: 400 (validation), 401 (unauthenticated), 403 (forbidden), 404 (not found), 409 (conflict).

5. **Note**: Reference Swagger UI for the definitive, always-up-to-date API documentation generated from source code annotations.

**doc/04-deployment.md — Deployment Guide**

Write a deployment guide covering:

1. **Production Stack**: Docker Compose orchestrates 3 services: app (Spring Boot JAR), db (PostgreSQL), pgadmin (PgAdmin web UI). All container names prefixed with `usermgmt-`.

2. **Prerequisites**: Docker, Docker Compose v2, configured .env file with production values (real DB credentials, SMTP settings, strong JWT secret).

3. **Configuration Checklist**: All env vars that MUST be changed from defaults for production:

   - SMTP_* settings (real mail server)

5. **Management Commands**: up, down, logs, status, restart via run-prod.sh subcommands. Direct docker compose commands for advanced use.

6. **Health Checks**: App uses /actuator/health, PostgreSQL uses pg_isready. Docker Compose depends_on with condition: service_healthy ensures proper startup order.

7. **Troubleshooting**: Common issues — port conflicts, template not substituted (stale config), Docker not running, database connection refused (startup order).
